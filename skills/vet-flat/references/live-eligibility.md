# Connecting live candidates to current conditions

`scripts/live_eligibility.py` is an offline adapter around [eligibility-api.md](eligibility-api.md). The local research interface calls it before delivering a comparison. Downloading the script alone does not install these checks into another agent host.

## Host responsibilities

1. Save every exact user message in order, including interruptions. Reconcile durable state before dispatch. Capture a new intent revision immediately when input arrives; an older in-flight answer cannot remain current. When the UI sends a known current host question plus the user's answer, retain the full exchange for audit but normalize only the answer. Do not reinterpret the host's question as a newly asserted human condition.
2. Let the actor discover up to three candidate URLs and select relevant comparison fields. The proposal has only `candidates: [{source_url, label}]` and `focus_fields`. Reject actor-supplied facts, constraints, exceptions, ranks, tasks or free-form final prose. Labels are private discovery hints and do not become verified property names.
3. Independently retain the source text, URL, retrieval time and SHA-256. A source entry has `text`, `retrieved_at`, `sha256`, `ok`, `identity`, and optional `note`. The local interface uses its bounded public-source capture helper. This script does no networking. Check the helper's allowlist separately; a valid HTTPS URL alone grants no retrieval authority.
4. Call `accept(proposal, user_inputs, revision, sources)`. It normalizes the supported phrases, extracts limited advertised facts, evaluates all recorded checks, validates the recommendation, and renders the visible comparison and tasks from that result.
5. Persist the complete artifact before publishing its reply. Validate it again using `validate_artifact(artifact, user_inputs, revision, sources)` against independently retained current inputs. A hash computed from actor-owned replacements is not an independent pin.
6. Recompute after input, evidence or code changes. Preserve historical replies and raw proposals, but never export an old comparison as current. Missing/corrupt required capture records stop acceptance; do not fall back to an older success. Account for a completed discarded call before starting another call.

## Supported meaning and limits

- Explicit rent ceilings and explicit total-monthly-cost ceilings are separate. Generic “budget” remains ambiguous. The adapter recognizes a limited set of English/Chinese numbers, bedrooms, floor ranges and minimum area phrases; it is not a general natural-language interpreter.
- Keep unsupported clauses and conditional changes as unresolved intent. Do not silently waive a previous condition. Later explicit changes affect only the recognized field and scope. “Rent must include heating” is not erased by a later rent ceiling.
- A narrowly recognized question such as “Is heating included in the rent?” is a request for source information, not a housing condition. The latest supported question per field retains its exact user-message origin and is answered for the current candidates even if the actor omits that field. A missing answer creates a separate information research task only for candidates still under consideration; it cannot change eligibility, ranking or the rent ceiling. This is currently limited to the supported heating-inclusion questions, not general conversation or arbitrary candidate-specific targeting.
- The core eligibility API supports trusted scoped exceptions. This automatic live adapter does not infer or activate such exceptions from arbitrary conversation. Use a separately reviewed host reconciliation for advanced predicates; do not ask an actor to invent a waiver.
- Advertised prices, bedrooms, floor and areas remain `reported`. Values outside a hard limit block a candidate; values inside a limit still need verification. An advert's marketing phrase does not establish quietness, insulation, bill inclusion or availability on a requested date.
- A host/page-shape check that a page describes one unit is not verification of the unit's physical facts. Multiple units, conflicting values, “from” prices and unsupported page layouts remain unknown. A page can be misleading despite passing these checks.
- The small candidate pool is for further investigation. Sorting uses failed-preference count, open-check count, advertised rent and a stable identifier, not inferred user priorities or a universal housing-quality score. Previously retained candidates cannot disappear merely because an actor omits them. Exceeding the current three-candidate pool stops instead of dropping a candidate silently.
- The managed comparison reply is generated by the program. This binds its claims, ranking and tasks to one artifact but limits open-ended conversation. Arbitrary model prose in another file or host is outside this guarantee. A native agent may explain broader topics, but must not call an unchecked answer a validated comparison.

## Python and CLI

The Python API returns JSON-serializable dictionaries. `normalize(user_inputs, revision)` exposes the current supported requirements, exact provenance and unresolved clauses before dispatch. `sources` is a URL-to-source-object map. `validate_artifact` recomputes the entire accepted object; changed reply text, ranking, tasks, evidence metadata or input revision fails equality.

`normalize` also returns `information_requests`, each with `id`, `field`, `request_id`, exact `quote`, and `scope: "current_candidates"`. The accepted artifact adds `effective_focus_fields` (actor focus plus these user-requested fields), `inquiries` (one source-qualified answer per request and candidate), and `information_todos` (separate research obligations). Inquiry statuses are `unknown` or `source_reported`; every answer retains its source quote when available, user-question origin and current pins. `recommendation.todos` remains eligibility-only. `presentation.todos` combines readable eligibility and information tasks for both the reply and host panel; `presentation.information_todos` exposes the information-only subset. All of these fields are recomputed during validation.

```bash
python3 "$PEA_SKILL/scripts/live_eligibility.py" --help
python3 "$PEA_SKILL/scripts/live_eligibility.py" accept --help
python3 "$PEA_SKILL/scripts/live_eligibility.py" validate --help
```

Write a private request JSON object with exactly `proposal`, `user_inputs`, `revision`, and `sources`; these are the same Python arguments described above. After preparing those trusted inputs:

```bash
python3 "$PEA_SKILL/scripts/live_eligibility.py" accept --input "$PRIVATE_REQUEST" > "$PRIVATE_RESULT"
python3 "$PEA_SKILL/scripts/live_eligibility.py" validate --input "$PRIVATE_REQUEST" --artifact "$PRIVATE_RESULT"
```

Exit 0 means the operation completed (or validation accepted), not that a property passed every condition. Validation rejection exits 1; malformed input exits 2. JSON is written to stdout, input errors to stderr. `presentation.conditions` and `presentation.todos` provide the same readable conditions/tasks for a host panel; complete raw clauses remain in the artifact even when the conversational reply shows excerpts.

Keep input/output files in the user's private working project. These checks do not prove the source is truthful, authorize contact/payment, prevent a same-user process from rewriting files, or replace the host's permission controls.
