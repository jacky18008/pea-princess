# 對話評估流程：root 獨立複核

2026-09-09。這份文件記錄評分過程本身的問題與更正，避免把 AI 裁判的輸出直接當成真值。正式矩陣仍在進行，以下三個開場的觀察不是完整消融結果。

## 評估的責任與證據

GPT-6 Astra evaluator 使用新建、沒有設計者完整上下文的子代理。它先看匿名對話、當輪可用來源、工具紀錄，以及真正保存的產物；root 另查原始計畫、請求、產物和評分依據。root 知道組別，因此 root review 不標成盲評。主評分、後續更正與 root 分歧分開保存，不回寫原評分。

6 個作者編寫的校準例子是理解評分規則的檢查。作者預期答案可見，沒有真人標籤，不能稱為獨立校準準確率。24 個正式配對會另行執行；同模型家族的 evaluator 仍可能有共同偏誤。

## 已發現並更正的封包錯誤

暫評封包產生器把三個開場的 `mode` 都填成 lite。root 核對凍結 `plan.json` 和原始 `request.json`：I03 實際要求 deep，產物的 `internal_depth=deep` 和工具 `--tier deep` 一致。這是**評估封包的標籤錯誤**，不是回答模型違反使用者要求，也不是原生 runner 配置錯誤。I01、I02 的 lite 標籤正確。

原始三個封包及原評分保留，另存更正附註；正式配對產生器從實際 session 讀深度，已核對不使用這個寫死值。深度相關的扣分需重評。即使仍認為筆記重複，也必須按 deep 的必要查核範圍判斷，不能把工具多或文件長自動當成浪費。

## root 與 evaluator 的判斷分歧

I01 的連結文件有「符合已知硬條件」，同節卻明確標示 CONDITIONAL、待確認安靜與帳單。另把「樓層先抓二樓以上」寫成 KILL。root 確認原文確實如此，認為有以下可直接採用的缺陷：

- 暫定樓層偏好被硬化，削弱後續協作與需求忠實度。
- 「符合」與「待確認」放在一起，沒有清楚說明只符合哪些結構條件；不利於使用者理解證據範圍。
- 在目的地未知時，以房東通勤估計引導安靜／交通取捨，決策依據不足。

但原文整體仍是暫定候選排序，沒有聲稱可以放心承租或已證實安靜。root 因此**不直接採納 G1、G3 同時失敗的強判定**；較確定的是 T6 證據措辭及需求連續性的缺陷。要判 gate failure，必須再指出實際推薦如何違反必要條件、或如何把未證實事項認證為真。單一模糊句不應被當成兩個獨立失敗案例。evaluator 已受邀保留自己的更正或不同意見。

evaluator 已另存獨立重讀附註：I03 的 S4 從 1 修訂為 2；I01 的 T6 從 0 修訂為 1，撤回 G1／G3 failure，任務成功由 false 改為未可評的 null。原評分不動。root 另做 27 段引文與 17 個產物的逐一比對，全部吻合；這只支持證據可追溯，不表示分數已有人工真值。

這不表示文筆能抵銷錯誤。後續若預算確實超標仍推薦為符合、全域移除只適用一間的例外，或宣稱未執行的動作完成，應依原 rubric 判定，不因語氣友善放過。

## 正式評分需要核對的項目

1. 引文必須在指定訊息或實際檔案中出現，並讀上下文。SHA 相符只證明檔案一致，不能證明判斷正確。
2. 共同前三輪和九輪延伸分開；不可用後來才有的證據懲罰早期合理暫定答案。早期本來就需更多查核，不等於失敗。
3. `questions=[]` 只表示沒有結構化選項欄位。原生 CLI 的文字問題仍須閱讀；問號數和未來要問房東的資訊清單不等於當輪要求使用者做的決策數。
4. 工具開始／完成事件不可算成兩次執行。頂層成功也不保證每個子命令成功；對保存、查核與計算的宣稱，需要實際產物及相關輸出。
5. 私有完整筆記的長度與使用者當下看到的負擔分開。研究深度決定查核範圍，不要求把全部底稿貼進回覆。
6. 自動產生的使用者感謝或長度反應只能算腳本訊號，不能當真人滿意度、正確性或成功率。
7. 未評、未觀測、沒有機會與失敗分開列分母。每格一個合成情境，沒有獨立重複；不能用描述性平均分證明一般品質等效。

完整工具文字可能暴露原技能措辭、深度及產物時間，因此只能稱為隱藏身分映射的部分盲評。刪除這些證據雖可能讓匿名更好，卻會降低核對實際行為的能力；本輪保留完整證據並揭露限制。
