## Handing a listing page over (the author's question of 2026-09-17)

The public skill never fetches listing sites (SECURITY.md; the author's 2026-09-03 rule) and that stays. What
gives the agent as much as a crawler would see is the person's own browser: on the listing page, File → Save
Page As → "Webpage, Complete" (.html), then attach the .html (plus a print-to-PDF for the photos and the floor
plan). Portal pages embed a structured data block with more than the screen shows (price, rooms, floor plan
and photo URLs, EPC and council-tax bands, deposit, availability, agent, coordinates, nearest stations);
`scripts/listing_fields.py` reads it, and refuses a URL.

Tested the same afternoon on one real saved portal page (Chrome, "Webpage, Complete"; the page stays
outside the repository). The `.html` carried the whole data block (104 KB, index-referenced array inside
a JSON string): full postcode where the screen showed only the district, coordinates (marked approximate
by the page), three nearest stations with distances, all six photo links, the EPC chart link, deposit,
availability, let type, listing date, agent company and phone. The folder beside it held four of the six
photos (the ones on screen) and no EPC chart. The parser before the fix read 5 fields and returned the
agent's office postcode as the property's — the vetting chain would have scanned the wrong district.
After the fix (this branch): 12 of 16 fields, the property's full postcode from the block, the office
postcode excluded (`other_district`), label-then-value grids read correctly ("BEDROOMS 2 BATHROOMS 1"
no longer gives bathrooms = 2), "second-floor" read as floor 2, "Deposit: £ 500" and "6 weeks' rent"
read, a glossary sentence after "council tax" no longer read as band A, the document title no longer
polluted by icon titles. `vet_case.py --listing` had passed the raw bytes and the wrong kind to the
parser (every saved page silently gave nothing); fixed and tested. The `page` block lists links for the
person; the reference text says never to fetch them. Phone users: the share sheet's PDF or the copied
text carries no data block. Done the same afternoon (author: "do it now if it is easy"): (1)
`scripts/capture_page.js` — an iOS Shortcut ("Run JavaScript on Web Page", build steps at the top of the
file) or desktop bookmarklet that serialises the open page into one `.txt` (HTML inside: title, meta,
JSON-LD/JSON blocks, inline data assignments, visible text, image links), no request of its own; checked
in headless Chrome on the same real saved page: 120 KB out, 3 data blocks, and `listing_fields.py` read the
identical 12 fields and page block from the capture as from the saved `.html`. Not yet run on a real
iPhone — the author's first Shortcut run is the remaining check. (2) `.webarchive` reading in

--max-processed-tokens 12000000`, then `python3 bench/release_gate.py <folder>/results/durable`. The runner
