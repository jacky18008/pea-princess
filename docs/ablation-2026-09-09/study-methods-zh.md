# Ablation study：設計、成本口徑與可推論範圍

本文件把已凍結的 [protocol](protocol.md) 說明成中文，方便閱讀結果時辨認哪些差異真的是被移除的組件造成、哪些因素仍綁在一起。它沒有更改實驗條件；最終數字另見 `results.md`。本次不用 Claude，先前七場 Claude 確認試驗維持暫停。

## 這次「完整」的意思

跑完事先宣告的矩陣，包含對照組、記憶 metadata 的 2×2 交互作用、兩輪對話、重複生成，以及檢索的短／長文件條件。這不是把所有模型、壓縮器、檢索器和真實使用情境都排列一遍，也不是足以宣告品質等效的大樣本研究。

| 區塊 | 固定矩陣 | 最多 CLI 呼叫 |
|---|---|---:|
| 裁判校準 | 4 個舊案例 × 2 版裁判 | 8 |
| 租屋記憶 | 3 個新案例 × 2 輪 × 2 次重複 × 6 組；另計生成與裁判 | 96 |
| 文件檢索 | 3 個新案例 × 2 種長度 × 6 組；另計摘要、可選第二次呼叫與裁判 | 54 |
| 合計 | 108 份最終答案、18 次新案例評分 | 158 |

答案、記憶和摘要都由 `gpt-5.6-terra` 產生；裁判使用 `gpt-5.6-sol`，全部 effort=`low`。這些是送給 CLI 的模型名稱，沒有獨立證明服務端的內部修訂版本。每次啟動都是新的 CLI invocation，不會把同一 thread 的多筆累積 usage 再相加。

## Controller 實際整合了什麼

新的 runner 真的使用 `CallControl`，每次實體模型呼叫有獨立 ID，另外保存其 logical job、角色和階段。它在呼叫前寫入 dispatch checkpoint，完成後才保存結果；重複送達與已完成 checkpoint 不會重跑 callback。發生失敗或直接 usage 缺失時，後續呼叫暫停；恢復時遇到尚未完成的 dispatch 也不會偷偷重試。

這是把先前已測試的 reducer 接到執行邊界，驗證持久狀態和成本去重。舊 runner 本來已有 Python 統計及部分停止保護，因此不能把整合本身說成新得到一次 85% 的 token 節省。檢查發生在 subprocess 完成後，沒有測量串流中斷的即時偵測速度、通知延遲或分散式多機競爭。

## 記憶組：控制相同內容，移除兩種 metadata

每個案例／重複／輪次用一個共同生成器，同時產生短篇敘述與最多 48 筆 fact rows。第一輪只看原始使用者歷史；第二輪更新時只看前次完整記憶和第一輪使用者訊息，不能看第二輪的新問題或標準答案。

| 組別 | 答題時可見內容 | source ID／quote | status／supersedes |
|---|---|---|---|
| full | 完整使用者歷史 | 原始訊息 | 原始訊息 |
| prose | 自動短篇敘述 | 視生成結果而定 | 視生成結果而定 |
| state | 共同 fact rows | 保留 | 保留 |
| state_no_sources | 相同 fact rows | 移除 | 保留 |
| state_no_updates | 相同 fact rows | 保留 | 移除 |
| state_neither | 相同 fact rows | 移除 | 移除 |

四種 state 的 fact ID、key、value、qualification、順序完全相同，只移除指定欄位。因此可以比較「答題模型拿到這些 metadata 有什麼差別」。`state_no_updates` **仍然經過更新**；它只是看不到明示的替代關係。共同更新器始終拿得到完整 metadata，這不是四個不同的端到端壓縮器。值與排列順序也可能透露新舊順序。

第二輪各組還會看見自己的第一輪回答，明確標示為先前 assistant 輸出，不當成來源。這符合短期接續對話，但也讓第一輪回答可能補回被移除的資訊；不能把 metadata 效果很小解讀成長期記憶不需要來源或版本。

`prose` 與 `state` 的資訊保留可能不同，所以兩者差異包含內容與表示方式，不是只改 JSON 或文字格式的純語法實驗。生成器為兩種輸出共同設計，因此它的成本也不能代表專門優化過的純文字摘要器。

以同一案例／輪次／重複配對，令 S、NS、NU、N 分別代表上述四種 state：

- source effect = `((S − NS) + (NU − N)) / 2`
- replacement metadata effect = `((S − NU) + (NS − N)) / 2`
- interaction = `S − NS − NU + N`

品質的正值表示保留欄位後得分較高；token 的正值表示保留後較耗。會分開呈現第一輪、第二輪及重複差異，不把相依的輪次當成獨立受試者計算狹窄的信賴區間。

## 檢索組：先分清楚摘要、選文件與額外呼叫

每個案例都有相同問題、判準和關鍵證據的 short／long 兩版文件。短版全文是長版的完整前綴；長版新增不同的營運背景，沒有新增改變結論的關鍵事實。文件 ID、標題及關鍵證據位置結構沒有重新隨機化，因此這不是全面的長上下文 needle-position 測試。

| 組別 | 答題證據 | 額外模型工作 |
|---|---|---|
| raw_full | 全部四份文件 | 無 |
| full | 四份文件＋自動摘要 | 生成摘要 |
| summary | 摘要＋文件目錄 | 生成摘要 |
| lexical | 摘要＋固定文字 ranker 前兩份 | 生成摘要；ranker 是 Python |
| adaptive | 摘要／目錄，可要求至多兩份文件 | 生成摘要；至多一次後續答題呼叫 |
| oracle | 摘要＋事先指定的兩份必要文件 | 生成摘要；文件選擇有標準答案特權 |

摘要器看到所有文件，但看不到問題或 gold。摘要遺漏也保留原狀。`raw_full` 不需要摘要，成本不能硬加上摘要器。`oracle` 用來觀察選文件的理想上限，不能直接當成可部署的檢索器。

`adaptive` 若第一步就回答，省下的第二次呼叫會明列為 skip；不會為了湊滿 158 次而強迫再呼叫。若選錯文件也不額外補救。與 oracle 的差距同時包含選擇、兩步輸入與額外呼叫成本，不能歸因為單一原因。兩種長度、每格一次答案，最多能顯示這幾個配對在何處變化，不能推估普遍適用的損益平衡曲線。

## 成本有兩個帳本，不能混加

**本次實際 CLI 總量**：把每個真正發生的 invocation 算一次，包括生成器、答案、裁判和校準。共同生成器只計一次。

**單獨採用某組的 pipeline 成本**：該組回答所需的所有答案呼叫，加上必要生成／更新呼叫；同一生成器在該組內只算一次。第二輪不能把第一輪的生成再算第二遍。比較節省時使用這個口徑。

不同組共用生成器，因此各組 standalone 成本有重疊，**不能把各組成本加起來當實驗總成本**。共同生成器同時輸出 prose 與 facts；為避免藏成本，單獨採用任一壓縮組都負擔完整生成器成本。這對專門的純 prose 壓縮器是偏保守的估計。

Processed tokens 是直接 terminal event 的 input＋output。Cached tokens 已包含在 input，reasoning 已包含在 output，不能再加。這不是帳單金額，也不能直接換算訂閱額度。主對話、fixture 編寫、子代理 code review／來源複核及報告撰寫，不在這次受測 CLI 帳本內；本機 Python 工作另計，沒有模型 tokens。

## 品質需要三層檢查

每個新答案有五個事先指定的 required findings，其中部分是 critical；另有六個 scalar 欄位做確定性檢查。字面／格式檢查可能把語義等價答案算錯，遇到時保留原始分數，另列語義複核。反過來，scalar 正確也不能抵銷正文的錯誤。

主要語義評分由匿名候選的模型裁判完成。新裁判同時看來源與各候選實際拿到的證據，避免把「沒有拿到文件」誤判成「捏造自己沒看過文件」。校準使用的是已知四種舊錯誤，而且同時改了可見證據和評分規則，所以不是只改 visibility 的因果實驗，也不是對新錯誤的獨立準確率驗證。

另在新案例答案出現前，固定選定六組、共 36 份答案做來源複核；所有組別候選都保留，不挑最好或最差者。複核者不看實驗 arm、成本或主要裁判結果，也不複核自己編寫的案例。證據形式仍可能透露組別，所以匿名並不完美。這仍是 AI 來源複核，沒有人工 ground truth。所有 scalar 不符或重要裁判標記，再做明示為事後選樣的針對性檢查。

## 採用門檻

可實作的候選組必須同時符合：standalone pipeline 至少節省 10%、沒有新增配對 critical omission、整體 scalar 正確數不下降、來源複核的無根據重要主張沒有增加。基準為租屋 `full`、檢索 `raw_full`。Oracle 不具採用資格。

通過也只足以支持下一個有限範圍的驗證；不等於品質保證、真實租屋法律判斷正確或使用者滿意度相等。若全部組別未過，就如實保留這個結果，不追加生成直到過關。
