## 2. 我們到底比較了什麼

試驗問題是：把例行進度留在程式中，模型只接收必要統計，能否保留報告的正確性並降低用量？
這次使用已保存的三批 persona 結果，重新請 Codex 產生狀態報告。
沒有重新生成任何租屋對話，也沒有重新請模型替租屋回答打分。

來源是 9 月 8 日以同一套確定性規則重評、且與原始資料分開保存的 scorecards：

先前把兩組簡稱「舊／新方式」，應理解為兩種協調方式的比較，不是歷史帳單的反事實重算。

首批最終報告先完整、後精簡；後兩批交換順序。

這裡的「最終回答」是 `answer.txt` 中的固定結構 JSON，
不是本次聊天中的自然語言說明，也不是房源審查全文。

### 3.3 為什麼這份品質證據有邊界

這是相對容易、明確定義的報告任務。幾乎所有數值已由程式算好，
模型主要負責遵守欄位規格及套用簡單的三分支決策規則。
原 runner 的 `facts()` 同時用於準備統計與產生預期結果；
若兩處都依賴同一個錯誤，單看 pass 會有自我驗證的問題。
因此本次另從原始 scorecard rows 獨立重算，再查全部十份回答，結果一致。

獨立重算能確認統計沒有算錯，但不能證明歷史模型裁判的主觀判斷或
安全線文字規則代表了真實租屋品質。原始裁判錯了，兩組仍可能同樣忠實地報告錯的來源。

本次沒有評估：閱讀原始對話後的診斷、跨 persona 的模式、自然語言說明完整度、
證據引用、法律事實、使用者滿意度、即時事故通知、開放式權衡。
兩組本來都被要求只回 JSON，所以不能以輸出相同來推論長文分析品質。
只有三個最終配對、每組各執行一次；沒有估計失誤率，也沒有建立統計上的等效性或非劣性。

**更精確的回答是：這三份固定報告的品質相同；完整產品品質是否相同，目前尚未量測。**

## 4. Token 為什麼變少：分解數字

| 資料組 | 完整組全部回報 | 精簡組最終回報 | 減少 |
|---|---:|---:|---:|
| 首輪 32 場 | 138,987 | 14,910 | 89.2724% |
| 修補後 32 場 | 136,293 | 14,916 | 89.0559% |
| 七場供應商失敗 | 26,979 | 15,016 | 44.3419% |
| 合計 | 302,259 | 44,842 | 85.1644% |

可以沿著同一份已量到的資料做一個算術分解：

```text
完整組全部七次          302,259
扣掉四次例行中途回報   −163,188
完整組最後三次          139,071
換成精簡組最後三次      −94,229
精簡組最後三次           44,842
```

四次中途回報占原比較基準的 53.99%；最後三份報告的輸入差異再占 31.17%。
兩者在這個算術路徑上合計 85.16%。若分母只用完整組的三次最終報告，
精簡組是 **139,071 → 44,842，少 67.7560%**。

這不是完整的兩因素隨機試驗。完整組最終 prompt 仍含之前的回報，
上述分解沒有另外實跑「移除中途回報後重新產生的完整最終 prompt」。
所以它能解釋已量到的 token 去向，不能把兩項視為可獨立相加的普遍因果效果。
85.2% 與 67.8% 使用不同分母，更不能相加。

兩組總共差 257,417 tokens，其中 input 差 256,827，
占節省量 **99.77%**。最終三份回答的 output 都是 489。
這次主要省的是反覆讀入資訊的工作，沒有靠刪掉最終報告內容換取低用量。

最終 prompts 的程式可見字元數也反映這個差異：

| 最終報告 | 完整組 prompt 字元 | 精簡組 prompt 字元 |
|---|---:|---:|
| 首輪 | 140,493 | 1,879 |
| 修補後 | 141,483 | 1,891 |
| 七場失敗 | 49,243 | 2,055 |

字元不是 tokens，prompt 檔也不包括 CLI 注入的所有內容。
精簡 prompt 只有約兩千字元，回報 input 仍約 14,800 tokens，
表示光看自己撰寫的文字不足以估算整次呼叫；本次沒有把剩餘開銷逐來源拆解。

時間方面，精簡組總和較短，部分來自少了四次程序與請求。
不能據此保證每次都更快：修補後最終配對的精簡組是 12.574 秒，
完整組是 12.471 秒，該次精簡組反而略慢。小樣本、啟動與供應商波動都會影響結果。

## 5. 計量方法、快取與試驗本身的成本

本次每次獨立 invocation 取最後一筆 `turn.completed.usage`，
processed 定義為 `input_tokens + output_tokens`。
cached input 與 cache-write input 是 input 的細分，reasoning 是 output 的細分，
不可再加一次。原解析器的重複加計已在試驗前以 `ba94d98` 修正。
[官方 Codex JSONL 說明](https://learn.chatgpt.com/docs/non-interactive-mode)與
[官方 usage 結構範例](https://developers.openai.com/api/reference/cli/resources/responses/methods/retrieve)
可對照這些欄位；本次原始事件均有完整計量。

正式十次呼叫的 reasoning 與 cache-write counters 都是 0。
解析器修正是避免未來誤算的防護，並非這次 85.2% 節省的來源。

| 計量項目 | 完整組 | 精簡組 |
|---|---:|---:|
| Input | 301,180 | 44,353 |
| Cached input，已包含在 input | 0 | 24,064 |
| Cache-write input，已包含在 input | 0 | 0 |
| Input 扣除 read cache | 301,180 | 20,289 |
| Output | 1,079 | 489 |
| Processed | 302,259 | 44,842 |

85.2% 已包含 cached input，不是把 cache hit 當成免費或不算 token。
但兩組快取表現不同，不能把 processed 的節省率直接換成費用或訂閱額度節省率。
官方快取文件分別提供 input、cache read、cache write 的計量及費用計算方式；
這是不同的量。[官方 prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

先前 Claude 審查使用另一種原始 schema：fresh input、cache creation、cache read、
output 分欄相加。跨供應商應先按欄位語義正規化，不能直接把本次 Codex 的加總公式
套到 Claude 原始欄位，也不能把同一事件的 session log、scorecard、summary 重複相加。

本次正式呼叫 347,101，加 canary 14,040，共 361,141 CLI processed tokens。
不包含建置、分析、寫文件的主對話與協作代理用量。
所有正式呼叫一次完成，沒有為通過品質門檻而重跑，也沒有未知用量被填成零。
未曾觸發 600,000 已回報 tokens 的停跑門檻；該門檻在呼叫之間檢查，
不是單一請求的硬上限。每次 timeout 為 180 秒。

## 6. 與先前 token 暴增的關係

以下是既有本機紀錄的審查結果，用來解釋改善方向，與本次 Codex 對照分開計算：

| 已保存的證據 | 代表的問題 | 對應做法 |
|---|---|---|
| 兩輪 64 場有 487 個受測 agent 回合 | 場次遠少於實際呼叫數 | 預算納入回合數及各角色 |
| 成功 response 實際為 `claude-opus-5`，文件卻寫 Sonnet | 文件與真實模型身分不一致 | 明確指定模型並保存實際回報身分 |
| 混合控制對話 input context 中位 531,375 tokens | 每次簡短回報可能仍讀入很長歷史 | 新階段採短交接，只帶決策所需證據 |
| 控制對話 335 次 Monitor 通知 | 沒有實質變化也反覆啟動模型 | 程式記錄進度，事件需要判斷時才通知 |
| 獨立 benchmark 約 8.07 億 processed，93.74% cache read | 有快取仍會大量重複處理 | 先減呼叫次數與上下文，再考慮快取 |
| helpers、早期重試、timeout 計量有缺漏 | 報表低估整套工作的已知消耗 | 每個角色、每次嘗試保存計量及缺失狀態 |
| fix2 七場全是 provider failure | 基礎設施失敗被持續排程 | 保存失敗、停批次、服務恢復後限量確認 |

混合控制對話含其他專案，不能全歸因於 pea-princess。
DNS 是最後七場失敗的原因，沒有證據足以把整週用量暴增都歸因於 DNS。
也不能拿本次 85.2% 乘上 8.07 億，宣稱當時一定能省下那個數字。
完整來源、去重與歸因方法見 [先前 token 審查](../handoff/2026-09-08-token-audit.md)。

## 7. 可以採用的 insights，以及適用條件

### 固定統計與已知規則可以直接由程式完成

本次 `facts()` 已能產生所有要求的報告欄位及 `decision`。
如果產品只需要這個 JSON，模型呼叫可以直接省略，由 Python 輸出結果。
這是從程式可確認的設計選項，**不是第三組已實跑的模型試驗**，
也不是整個租屋工作都能達到零 token。

保留模型的合理用途包括：解釋異常、閱讀相關對話找原因、比較修補方案、
把結果寫成對使用者有幫助的說明。先定義需要什麼判斷，再決定是否值得呼叫。

### 保存完整紀錄，送入模型的內容按用途選取

原始 prompts、對話、卡片與用量都應保留在檔案中，方便重現與事後查證。
例行回報先提供聚合統計、失敗 IDs、版本與證據位置。
出現需要逐場判讀的問題，再讀相關原文；不要因為存了全部資料，就每次全數貼入上下文。

這份精簡 schema 並未保留所有有用分析：例如哪些 persona 退步、哪些分數與主觀滿意度
矛盾、哪段回答造成遺漏。這些任務需要額外欄位或來源片段，不能只靠現有統計硬下結論。

### 進度紀錄與模型通知分開

每場完成仍記 log。成功批次結束才整理報告；遇供應商失敗、資料不完整或需要決策時，
立即走對應事件處理。這樣保留可觀察性，也減少「再等一下」造成的模型呼叫。
本次成本試驗已驗證兩組成功批次的回報方式；真實事故通知延遲仍待另外驗證。

### 省成本時保持品質定義與實驗條件不變

先固定任務、模型、案例、評分標準與失敗處理，再改變協調方式。
失敗不能刪掉，低分不能一直重跑到通過，少提供資訊也不能同時降低評分要求。
本次十份回答均保留，完整與精簡組拿到相同統計，也用相同契約評分。

### 快取與小模型是下一層考量

本次沒有比較其他模型或 effort，不能據此宣稱另一個模型能維持相同品質。
快取也沒有解決不必要的模型喚醒。優先消除不必要的呼叫，再把必要呼叫的上下文縮到
足以完成任務；模型選擇與快取策略需要各自的對照證據。
