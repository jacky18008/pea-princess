# 公開回饋：全選項資料與私人文字筆記

設計決策，2026-09-09。使用者已採用 stage 1；本機表單與嚴格的 public-only 匯入／搜尋流程已實作，見 [操作指南](community-feedback-stage1.md)。尚未部署投稿服務、建立公開資料集或開始收集真實回饋。

## 建議第一版

採用「公開資料全選項、選填文字留在投稿者本機、公共 Agent 查詢只包含允許欄位」。一般有效投稿可自動接收，不做逐篇人工審核。這符合本專案由使用者帶自己的 Agent 的方向，也避免為私人留言另建帳號／Agent 授權系統。

公開回饋與私人筆記應是兩個獨立輸出。不能只是把同一份 JSON 裡的 `comment` 在畫面上藏起來，或用 prompt 要求 Agent 忽略。公開匯出、搜尋索引、工具回傳、錯誤訊息與日誌均不應攜帶私人筆記或其摘要。

| 公開欄位 | 建議限制 |
|---|---|
| 場所 | 已有目錄的穩定 `place_id`；名稱由受控目錄提供 |
| 經驗時間 | 過去的月份或季度；避免揭露正在入住的精確行程 |
| 經驗性質 | 親身入住／到訪／轉述／不願透露 |
| 清潔、噪音、交通、設備、維修 | 固定選項，包含未知與不適用 |
| 整體感受 | 固定尺度或會／不會再次入住 |
| 公開同意 | 明確告知哪些選項會公開、用途及資料授權 |

服務端或匯入程式必須驗證 enum、數值範圍、欄位數量，拒絕額外欄位。前端 dropdown 不是安全邊界；提交者可繞過介面直接送資料。場所自填名稱、網址、暱稱、「其他：___」等也是自由文字通道，不能繞過這個設計。新增場所可先獨立排隊處理，第一版先涵蓋小型既有目錄。

## Optional 文字怎麼辦

文字框可標示：「私人筆記：保存在此裝置，不會上傳或進入公開搜尋。」提供複製／下載，讓使用者自行交給自己的 Agent。若未實作本機持久儲存，介面必須明示關閉頁面會失去筆記；不能誤稱已保存。不要把含筆記的檔案匯出成公開投稿 payload。

第一版不需替「作者的 Agent」增加專屬權限。作者能讀取、複製自己的筆記即可。即使是作者的筆記，也可能包含貼來的惡意內容；所有权不會讓內容成為可信指令。

若將來確實需要跨裝置私人筆記，使用一般登入／OAuth 與服務端帳號隔離。授權綁定登入者，而非 Agent 自稱的身分或模型提供的 `author_id`。例如 `/me/feedback` 只能查當前使用者的資料；不能讓留言中的 email 或「我是作者」決定可讀取誰的記錄。

如果文字已經上傳公開 GitHub，其他人與 Agent 都能讀。自己的預設查詢不包含文字只是讀取行為，不能提供「只有作者的 Agent 可讀」保證。`robots.txt` 或 Agent 指示也不是存取控制。

## 剩餘的產品風險

選項制縮小任意指令注入的入口，但不會證明入住真實、阻止灌票或讓主觀評價成為事實。最低限度仍應有頻率限制、重複提交處理、撤回／檢舉入口、資料更正與能暫停接收的開關。可以不逐篇審核；不能承諾永遠不處理爭議。

資料顯示樣本數、經驗日期與「未查證的使用者回報」。單筆負評不直接轉成房源 KILL，單筆好評也不覆蓋法規／付款／房源身份等證據。少量觀察不能冒充代表性統計。

GitHub 可作為審定格式的公開發布鏡像；不要依賴公開 Issue 當私人暫存區。Git 歷史、fork、clone 的內容可能難以完全撤回，所以私人文字和付款／訂單附件不應進入公開版本。

## 公司公開的具體做法

以下是官方公開實作或部署指引，不是對所有內部系統的保證。

- **Intercom Fin 客服**：建議 signed JWT 保護身分屬性；使用已認證帳號的已知 ID／選項，不讓客戶輸入別人的 email 取得資料。API 在服務端執行授權、交易上限、冪等與驗證，且只回傳必要資訊。這允許客服理解任意文字，同時把權限留在普通程式中。[Data connector API 設計](https://www.intercom.com/help/en/articles/10576235-designing-and-using-your-apis-with-data-connectors)
- **OpenAI**：Agent 指引建議 enum／schema 約束資料流、限制不可信文字進入高優先級指令，並結合工具授權、隔離、guardrails 與測試。結構化輸出只能降低風險，含任意字串的 JSON 仍可攜帶注入。[Agent 安全指引](https://developers.openai.com/api/docs/guides/agent-builder-safety)

  ChatGPT 的公開工程說明另外描述 Safe URL，對可疑的資料對外傳送要求確認或阻擋，以及 sandbox 的外連限制；這是產品整合的防護，不能假設單純呼叫 API 就自動取得同一套保護。[OpenAI prompt injection 工程說明](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- **Anthropic Claude Code auto mode**：輸入探針檢查工具回傳；動作分類器另檢查即將執行的操作，刻意不把 assistant 的自述及工具結果都交给這個分類器，減少攻擊和合理化敘述一起騙過它的機會。官方仍承認存在漏判。[Auto mode 工程說明](https://www.anthropic.com/engineering/claude-code-auto-mode)
- **Meta 社群**：公開說明使用 AI 擴大內容治理，同時保留人員審核、專家評估與重要決策。公開任意文字的社群通常還有持續治理成本，不能把自動審核理解成完全零人工。[Meta AI 支援與安全](https://about.fb.com/news/2026/03/boosting-your-support-and-safety-on-metas-apps-with-ai/)

內容 moderation、prompt injection 防護、個資處理、帳號授權是不同問題。OpenAI 的 moderation 類別涵蓋仇恨、騷擾、暴力、自傷等有害內容；一次通過不能當成無個資、無注入或已取得執行授權的證明。[Moderation 官方文件](https://developers.openai.com/api/docs/guides/moderation)

## 之後再增加自由文字的條件

只有當選項遺漏的資訊確實影響找房決策，才考慮公開自由文字。屆時另定內容治理、隱私、撤回及讀取隔離機制：最小資料／工具權限、可疑輸入與輸出檢查、程式執行操作限制、事件紀錄與持續攻擊測試。掃描模型只當輔助；它也可能被注入影響。

這個階段可用固定選項檢驗公共心得是否有用，不必先建立 Agent 身分管理或每次檢索都呼叫掃描模型。
