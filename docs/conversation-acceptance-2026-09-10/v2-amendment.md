# V2：通勤證據適用範圍修正後的有限驗收

2026-09-10。這是對[原定驗收計畫](../conversation-acceptance-plan-2026-09-10.md)的明確修正。原計畫、原始對話、工具結果與獨立評分保持原樣。**V2 是針對已發現問題的修正驗證，不是全新保留測試集，也不是乾淨的品質／用量 A/B。** 本文記錄派送前的設計與離線 fixture 檢查，不代表新模型對話已通過。

## 原版為什麼停下來

原版已啟動 11 次原生 CLI 呼叫：兩次獨立的傳輸確認、A 的六輪、B 的前三輪。終態保存的原始 input + output counters 合計 **1,669,887**。計數範圍尚未完全確認，因此不能稱為精確 processed tokens、帳單金額或個人訂閱額度；主代理與評估子代理用量也不在這個 CLI ledger 裡。

獨立 Astra 評審的結論是：

| 已觀察範圍 | UX | 事實／證據 G1 | 授權／安全 G2 | 必要條件 G3 |
|---|---|---|---|---|
| A，六輪 | 通過 | 失敗 | 通過 | 失敗 |
| B，前三輪 | 失敗；第三輪首句 O1 未通過 | 失敗 | 通過 | 失敗 |

兩段都不能宣稱產品驗收通過；B 也只觀察到第三輪，沒有把缺失的後三輪評為通過。原判、精確引文與 validator 輸出保留在私人獨立評估資料夾。

共同問題是：資料給了某次路程的分鐘數，卻沒有指出它通往哪個目的地、對應什麼時段。原程式仍把數字拿來與使用者上限比較，模型也把這些觀察當成適用於使用者的通勤判斷。B 第三輪更直接在第一句據此排除候選，連帶使開場缺乏可靠依據。只標「一次觀察，不保證未來」仍不足以解決**這是不是使用者要走的路程**。

root 接受這項共通缺陷並在 B 第三輪後停止。原版九個未派送核心輪次與六個保留名額，不自動補跑，也不改寫成成功。

## 修正與新資料要分開看

修正版先檢查證據的適用範圍，才比較數字。通勤要求的目的地／時段未知，或證據與目標不相符，結果就是 unresolved；不能因為數字較小就判符合，也不能因為數字較大就排除。來源引文吻合與數字算對，不等於證據適用。這個修正延伸現有的日期／房間範圍檢查，保留原本的限定例外與證據資格。

V2 同時保留兩種診斷情境：

- **A、C 仍未提供目的地。** 通勤的未知狀態必須保留，其他已有依據的預算、面積與樓層條件仍可分析；不得憑空補一個目的地來讓程式通過。
- **B 前兩輪仍未知，第三輪才明確補上目的地、時段及三份相符的虛構觀察紀錄。** 這些是本次新增的證據，舊版未指明路程的來源文字保留為歷史；不能把新資料回填成舊版原本就知道的資訊。第三輪後才可以對該範圍比較數字，之後再納入原定的日間施工證據。

因此，V2 改了程式適用範圍檢查，也調整了 B 的使用者訊息與提供資料；每輪來源備註另明示通勤範圍未知或已補齊。對話風格指引不變，但整體輸入並非只改程式。若結果改善，不能全部歸因於某一行 prompt、模型本身，或聲稱同樣工作變得更省。

## 三段各五輪，完整保留被選中的需求

| 情境 | 保留的原版輪次 | 這次要檢查的事 |
|---|---|---|
| A：模糊的新手需求 | 1、2、3、4、6 | 先給例子，處理生活空間與採光插問，再留下理由、比較與待辦；通勤適用範圍保持未知。 |
| B：插問與優先順序改變 | 1、2、3、4、6 | 費用插問後接回主線；第三輪補上相符路程，第四輪納入施工，最後更新選擇與工作。 |
| C：預算、限定例外與重開 | 1、2、3、4、5 | 上限 2680 → 2580；補檢查後更新的總費用估計為 2610；再調上限 2720，重開後仍記得最新值與例外範圍。 |

V2 每段 revision 重新編為 1–5。每輪累積的 `user_requests` 只包括該段 V2 到當時真正釋出的使用者訊息；省略的舊輪次與未來訊息不混入。C 沒有原版最後調成 2800 的那一輪，不能把它當成目前上限。

C 仍只有指定候選可在限定條件下接受地面層：2026-09-09 的獨立觀察同時涵蓋臥室及客廳，且兩者當天乾燥。這不是其他房源的通用例外，不會放寬面積，也不保證未來不漏水。金額估計落在放寬後預算內，仍保留估計資格；不會升級成已確認的總花費。

原有角色、被選中輪次的偏好、非通勤事實、原始來源文字與乾燥限定條件保持不變。唯一新增的來源是 B 第三輪起明確指向新目的地／時段的三份虛構路程紀錄。

## 使用既有剩餘名額，不增加總上限

| 項目 | 本次安排 |
|---|---:|
| 原版已啟動 | 11 次 |
| 重新分配的原版未執行核心名額 | 9 次 |
| 重新分配的原版保留名額 | 6 次 |
| V2 新名額 | 15 次，三段各五輪 |
| 兩版合計啟動上限 | **26 次，不變** |
| 原始 input + output counter 停止門檻 | **8,000,000，不變，包含原版已記錄數值** |
| 再次傳輸確認／新保留名額／自動重試 | **0／0／0** |

這是操作上限重分配，不是新的財務預算授權。每次派送前重新核對原版停止紀錄、原始收據、用量和新版本身的呼叫數。未知用量、傳輸或輸入完整性失敗、共同的重大缺陷會阻止依賴的後續派送；不另增保留名額或默默重試。單次正在執行的呼叫仍可能跨過 counter 停止值。Claude 繼續暫停。

三段使用新的獨立 owned sessions；沿用既有傳輸設計，沒有新增傳輸確認呼叫。C 的第五輪從已保存的同一原生 session 恢復，並檢查最新條件、比較與待辦。它不等於強制壓縮、多日持續運作、手機能力或生成中即時插話已驗證。

## 保存與離線驗證

新私人資料使用獨立的 `conversation-acceptance-20260910-v2` 目錄：

- `make-fixtures-v2.py` 只讀取原版 `plan.json` 與 `v1-stop.json`，不執行或 import 原版 generator；輸出已存在時拒絕覆寫。
- `fixtures.json` 保存三段各五輪的完整資料；`amendment.json` 固定父停止紀錄 SHA、11 + 15 的分配及共同上限。
- `fixture-validation.json` 保存 15 輪離線重算結果、輸入與輸出雜湊、原資料未改動核對，以及作者所做的變更範圍。

離線檢查確認：未知目的地不作數字適配；B 新紀錄按當時明確範圍比較；後續施工排除仍有效；C 的估計費用、日期／房間條件與重開上限沒有遺漏。這些是程式與資料一致性檢查，**不是模型品質結果**。root 核對並凍結新版本後才派送；完整新對話交給獨立 Astra 評估，root 再複核評估流程與實際產物。由於案例已被看到並用於修正，後續通過也只支持這個範圍的修正驗證，不建立真人滿意度、跨模型能力或節省用量的廣泛主張。
