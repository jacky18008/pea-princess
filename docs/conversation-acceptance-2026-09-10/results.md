# 首句體驗、硬條件與多輪接續：驗收結果

這輪改善了已知條件的可靠性，也暴露「有用的完整回答」和「有吸引力的第一句」仍有落差。三段各五輪已完成：A、B 在有限案例內通過；C 的第 2、4 輪首句失敗，因此整包尚未通過體驗驗收。每輪 UX、來源與條件、最後產物必須分開看；不能拿正確的比較表替開場失敗加分。以下是本機檔案研究的有限驗收，沒有把虛構候選當成真實在租房源。

Actor 固定 GPT-6 Astra、low effort、Codex CLI 0.153.4。提供完整目前技能及合成來源，使用原生 shell／檔案工具。host 先捕捉作者撰寫的 user turn，再供應主代理核對過的正規化條件與證據；agent 寫實際 comparison、recommendation、TODO。它證明已知條件的執行及保存，不證明 agent 自動從自然語言抽取全部條件的能力。

每段是獨立的原生 session，後續明確指定同一 UUID 接續；每輪開新 controller process。只傳新輪次與當前權威檔案指標，沒有在操作層重貼完整對話。conversation guide 在開場前注入一次，使第一則 progress 也在規則範圍內。實際讀檔與工具結果仍會進入模型歷史；這個設計不等於每輪只花新訊息的 tokens。

## 原版失敗沒有被新版抹去

V1 A 的六輪 UX 通過，但事實／證據 G1 與硬條件 G3 失敗。B 只到第三輪，UX、G1、G3 都失敗：來源中的路程沒有目的地與時段，程式仍判通過／超時，B 甚至第一句就據此排除候選。註明「一次觀察，不保證以後」不足以補上「是不是使用者的路程」。

因此停止原版。V2 沒有偷偷補一個預設目的地：A、C 保持未知；B 第三輪才加入明確目的地、抵達時段與相符新紀錄。原始未指明路程的來源保留，不能把後來的新證據倒填成以前就知道。B 的輸入也因此改變，不能將前後差異全部歸因於程式修正，更不能宣稱同一工作省了 tokens。

## 新版實際觀察

### A：先給例子，再摸清生活優先順序

開場比較 Bay／Dune／Elms，費用、面積與噪音線索同時呈現，只問預算。使用者補上 £2,450、47 平方公尺後，Dune 因 44 平方公尺被排除，Elms 因估算 £2,550 超標被排除；「在家舒服」這項偏好不會推翻硬條件。

使用者插問通勤時間是否值得換小空間，agent 先回答取捨，不重開問卷。使用者要求用手邊資料看 Bay 採光時，agent 說明朝內院不等於暗、現有朝向描述不足以判採光，也沒有假裝看過未提供的照片。最後 Bay 優先了解，估算費用、通勤適用範圍、一月入住、安靜仍在未完成檢查與 TODO 中。

A 的獨立評審五輪 O1/U1–U4、C1/C2、G1/G2/G3 與任務完成均通過；root 接受這個有限結論。A2 首句雖在同一句把寫作／煮飯連到噪音與廚房檢查，但前半仍偏複述，只能算較弱的通過。額外方法公告和重複限制仍可精簡。

### B：插問後接回主線，新的證據改變排序

先以河邊散步與估算費用把 Grove 放前面。使用者問「租金低為何總花費可能更高」，agent 解釋帳單組成，也沒有捏造三間恰好出現反轉。前兩輪通勤目的地仍未知，所以不拿路程數字判定符合。

第三輪使用者改重視空間與採光、收緊通勤至 30 分鐘，並明確提供範例研究中心 R、平日 08:30 抵達及相符紀錄。此時才排除 45 分鐘的 Grove；Cove 的 30 分鐘只是相符的一次觀察，仍留下可靠性確認。第四輪 Quay 白天施工的文字紀錄與在家工作要求衝突，Quay 被排除，Cove 成為唯一優先查證候選。沒有把南向當成已證實採光佳，也沒有聲稱播放過影片。

B 的獨立評審五輪 UX、G1/G2/G3 與指定任務均通過，root 接受來源適用、排序與保存一致性的結論。B1 的第一句提供必要條件與生活偏好的區別，可以最低限度通過，但仍偏流程，不能當成高吸引力的示範。獨立 UX gate 只涵蓋可見聊天，未完整覆蓋保存文件的白話要求；root 因此不把這個局部通過擴張成整包產品通過。

### C：有限例外不是全體放行

初始 £2,680／49 平方公尺／不接受地面層，三間全部各有硬條件不符，沒有首選或備選。上限收緊至 £2,580，使用者只對 Sol 開放限定地面層例外：2026-09-09 獨立檢查必須同時確認臥室及客廳當天乾燥。證據尚未到時，例外不成立。

第三輪檢查到齊，樓層例外成立，但更新帳單令估算總費用從 £2,550 變為 £2,610，仍超過 £2,580。agent 正確把 Sol 的排除原因改成預算，並算出帳單仍估 £320 時租金需不高於 £2,260；沒有一關過了就全部放行，也沒有要求重交已提供的檢查。

第四輪只放寬總上限至 £2,720，Sol 才成為唯一待查候選；Maple £2,760 仍超標、Reed 47 平方公尺仍不足。Sol 未完成的費用核實、通勤適用範圍與安靜同時保留在回答、排序和 TODO。

第五輪從保存的同一原生 UUID 接續，回答最後 £2,720 及 Sol 唯一例外，沒有要求重填已知需求；日期與兩房間限定、舊費用被新估算取代的關係都保留。沒有真的關閉電腦；測到的是新的 controller 程序重新載入同一 session 和保存資料。

C 的獨立評審 **O1 第 2、4 輪失敗，整段驗收未通過**；其餘逐輪 UX、整段 C1/C2、G1/G2/G3 通過，指定任務完成。root 先前已自行指出相同兩句的複述問題，讀完原判後同意。C4 是嚴格首句要求下的邊界失敗，不是說整段回答很差；C5 則直接回答使用者正在問的最後上限，所以同樣是金額重述，此時有實際價值。

## 第一個回覆究竟好不好

完整首輪逐字例子見 [實際第一輪回覆](first-reply-examples.md)，包括真正先出現的進度訊息與後來 final，沒有潤稿。只展示最後比較漂亮的答案，會低估使用者實際承受的流程公告。

root 逐句核對後，C2 的真正第一句「預算改為每月 £2,580，49 平方公尺不變。」只有複述，沒有新增判斷或幫使用者看懂影響。第二句雖說明例外，不能替第一句補分。這是獨立 O1 失敗；其後正確的計算和狀態不能抵銷。

C2 的 factual prose、eligibility 及保存狀態沒有錯誤，因此繼續原有名額內的例外／預算／恢復觀察；執行 continuation receipt 不代表 UX 通過，亦沒有修改 prompt 或重跑 C2。這個區分及 root 決定在私人 root-review 保存。

另有兩項明確的呈現欠缺：第一輪中途仍說「依 vet-flat…」；B 的比較文件及 C 的部分文件出現計算工具內部識別字。原始證據原樣保留，不能宣稱回答與文件已全面沒有術語。這些文件應把可讀算式與必要來源留下，讓執行收據另外保存。

## 評估流程與限制

每個原生 `agent_message` 按原順序投影為可見，包括 progress，不假設 GUI 會隱藏。獨立 Astra 讀完整對話、實際當輪 source、工具、條件與檔案；不先看預期排序、root 打分、成本或未來 fixture。每輪 O1/U1–U4、整段 C1/C2 和 G1/G2/G3 分開判，全部適用門檻與任務完成都成立才可通過。精確引文、原判、驗證器結果與 root 分歧分開保存，不覆寫原始評分。

程式驗證引文、首則消息 ID、輪次完整性及門檻合併，不能以字數、問號數或關鍵字替代語意判斷。所有作者編寫的「好」「不用再問」只證明該腳本中的方向變更，不是真人滿意度、留存率或自主 user simulator。評審已知 V1 歷史，V2 是修正評估，不能冒稱全新盲樣本。

最後收據稽核通過：90 個 source pins、118 個原版綁定、三個互異的新 UUID 及後續同一 UUID 接續、180 個當輪封存檔案實例、33 則原生可見訊息與三份完整投影、102 個未來資料缺席檢查。完整 50 條 actor 命令經主代理與獨立子代理逐條語意複核；B2 有一次工作目錄內檔案不存在的查找失敗，沒有因此新增重試或丟掉紀錄。

沒有觀察到 actor 命令要求網路、無關檔案或外部操作；這不是 OS 隔離證明。B4 的 native stderr 有模型清單刷新子程序逾時，沒有子程序目的地資訊，因此不能宣稱整個原生 runtime 完全沒有網路活動。原生帳號側 session 儲存與憑證不在本次備份範圍，也沒有為了匯出而枚舉其他對話。

接下來優先順序：

1. 首句訓練／提示的對照應專門涵蓋「需求更新」：直接說其影響，不僅覆述。先保留這次原判，再做版本化新情境；不以人工潤稿的例句冒充模型已達成。
2. 把使用者 comparison／TODO 的內部執行識別字移到獨立收據，查明方法公告是否來自宿主規則；技能文字不能覆蓋宿主的更高層指令。未取得證據前，不把原因說成已確定。
3. 真正的本機互動驗收要用新的介面 session。現有 8765 網頁是 chat-only 測試台，與本次原生工具接續不同；本輪沒有證明它具備相同的條件檢查與寫檔能力，舊 session 也不會自動換成新版凍結提示。
4. 之後再以新情境測試真人選項互動、工具搜尋、缺失／衝突證據、自然語言條件抽取，以及真正壓縮／中途打斷。不在這輪擴增呼叫，也不先宣稱跨模型驗收通過。

本輪的重新接續是同機同一原生 UUID 加上保存檔案，沒有真的關機、強制壓縮、跨日持續、手機測試或在生成中插話。未更新主機上其他已安裝的技能副本；未推送或發布公開服務。
