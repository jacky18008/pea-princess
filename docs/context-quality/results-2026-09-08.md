# Context 與品質實驗：省下哪些 token，又漏掉什麼？

2026-09-08，`pea-princess`。三項授權實驗均已完成；**沒有使用 Claude**。
分析與租屋共 28 次回答呼叫、10 次盲評呼叫，已知 CLI processed tokens 合計 **669,726**。
另完成不呼叫模型的報表／控制器實驗。原定七場 Claude 確認保持暫停。

**結果不支持把上輪的「省 85.2%、最終報告相同」推廣到所有工作。**
這輪只給摘要的分析省 12.5%，但明顯漏掉原始證據；摘要再補查省不了 token，反而增加 81.6%。
租屋的固定交接摘要省 5.9%，核心決策大致保留，細節仍有遺漏與錯誤。最適合直接移除模型呼叫的，
仍是已知欄位的統計報表與明確的流程判斷。

## 2. 測試怎麼做，成本怎麼算

[事前 protocol](protocol-2026-09-08.md)、4 個分析案例、6 個租屋案例、問題、摘要、gold finding、
runner、計量 parser、固定入口指令與準備資料都有 SHA-256。程式及 protocol 先提交為
`d01c369a7d863aa920d8d90c0c2ec563228b8478`，再開始正式呼叫；結果出現後没有修改這些來源。

回答指定 `gpt-5.6-terra`、`low`；裁判指定 `gpt-5.6-sol`、`low`。
這是 CLI 請求的模型名稱，不是供應商內部版本的獨立識別。每次都是新的 CLI invocation，禁止 native tools。
依案例輪替回答順序；每題一次裁判同時看匿名候選答案、完整來源與已凍結判準，不看組別或成本。

分析組共用問題、摘要及目錄；完整組再拿全部三份文件。只有摘要組可誠實保留結論。
補查組最多選兩份文件，由程式提供所選正文，再執行一次最終回答；兩次都計入 token 用量，未選中的正文不會偷偷補給。
租屋組共用最後問題、英文回答指令及同一份 `dist/prompt-pack/INSTRUCTIONS.md`；差別僅為完整歷史或固定 handoff。

裁判另占整輪約 29.9%，沒有藏在比較之外。自訂上限為 38 次呼叫／開始下一呼叫前檢查 900,000 tokens，
單次 timeout 180 秒，沒有自動重試；本次在 38 次內正常完成，38 次都有有效的直接 terminal usage。
沒有 provider／turn 失敗、native tool event 或 Claude 呼叫。
不過，**34/38 次 stderr 有 CLI 模型目錄更新逾時診斷**；這些呼叫仍成功產生答案及 terminal usage。
「實驗成功」不表示 stderr 為空，也不能由此斷定那些診斷對耗時完全沒有影響。

補查組的 127,189 可拆成 **59,631 選文件＋67,558 讀入選定文件後回答**。

Processed tokens = 每次 `turn.completed.usage` 的 input + output。
Cached input 已在 input 裡，不能再加；reasoning 子項也不能再加一次。
缺少直接 terminal usage 會停下並保留未知值，不用中間事件的累積量補成看似完整。

## 3. 原文分析：補查提高發現率，但選錯文件仍會漏掉重點

下表品質為獨立盲複核，每題四項；原始裁判逐項結果保持在 [原始結果 JSON](live-results-2026-09-08.json)。

| 題目與必須看出的事實 | 完整：tokens／項目 | 摘要：tokens／項目 | 補查：tokens／項目 | 補查選擇與結果 |
|---|---:|---:|---:|---|
| A1：整體改善掩蓋 assisted 退步 | 17,479／3/4 | 15,305／1/4 | 31,540／2/4 | 選 D02、D03，漏選有關鍵 ledger 的 D01 |
| A2：3 PASS 與完整事件序列衝突 | 17,404／4/4 | 15,292／1/4 | 31,806／4/4 | 選 D01、D02，找出 provisional 報價及未批准更新 |
| A3：499/500 掩蓋受保存物件被列入移除提案 | 17,755／4/4 | 15,393／0/4 | 32,123／4/4 | 選 D01、D02，指出重要失誤，未誤稱已刪除 |
| A4：綠色敏感欄位清理標記不足以證明 token 是否送出 | 17,417／3/4 | 15,306／4/4 | 31,720／4/4 | 摘要已足以有根據地保留結論，仍選 D01、D02 |

**A1 是最有價值的失敗。** 總成功數 198/240 → 210/240，實際 assisted 卻由 28/40 降到 16/40；
相同案例及固定路由標籤排除了「只是樣本組成改變」的解釋。摘要與補查組都沒有讀到關鍵 ledger，
只能說「可能有子群問題」，不能說出已知退步。補查並非天然比完整輸入聰明：它先挑了路由與 release 記錄，
花了兩次呼叫仍漏掉主要證據。完整組雖發現退步，盲複核認為它没有明白交代固定配對的論證，故扣一項。

**A2、A3 顯示有原文與只有摘要的差異。** A2 的 `customer_confirmed` 是助理填入後被服務回顯，
不是使用者批准；使用者其實要求先不要改，報價 `final_total` 仍為 null。
A3 有重要的保存排除規則遭違反，但只到 preview／提案階段，寫入次數為零。
完整與補查組能找出這些具體事實；摘要組雖謹慎，没有完成事件層級分析。
不能因它没有亂猜就說工作已完成，也不能要求它捏造沒讀過的內容來取得完整分數。

**A4 顯示何時不必补查。** 摘要已明示 outbound payload、resolved token inputs、receiver field record 都缺少。
足以說「目前無法判定是否送出」，並條件式找獨立證據。補查四題全部觸發，這題也花兩次呼叫。
完整組建議查 build/config，但獨立複核認為這不足以補上 payload 層的驗證；原始裁判則給滿分。
這個差別保留為判準解讀分歧，不藉改 rubric 消除。

精確引用也有代價：A2 完整組把三段英文來源譯成中文放進 exact quote 欄位，
造成 **3 個引用字串檢查失敗**。內容意思有原文支持，屬引用保真失敗，並不是三個虛構事實。
其他分析組沒有不在實際供應來源中的 quote。程式只能驗證字串存在，語意支持仍需要來源閱讀。

完整／摘要／補查的關鍵項目遺漏，兩種評分都分別為 **0／3／1**。
完整和補查在盲複核同為 14/16，仍不能叫品質等效：補查的兩個遺漏集中在 A1 且含關鍵退步，
完整的兩個遺漏是 A1 的論證說明與 A4 的驗證方案。相同總分可能隱藏不同後果。

| R5：已更正預算、面積與目的地 | 18,191／17,073 | 5/5、4/5 | 交接未清楚解釋面積／studio 條件改變，並假設存在陽台 |

兩個 R3 答案都把使用者原本 **40 m²** 的最低面積說成 **42 m²**，混淆了門檻與 B 房源的面積。
這次没有改變選房結果，但是真正的來源錯誤；原始裁判漏抓，獨立複核抓到。
不能把完整歷史組當成 ground truth，也不能因兩組選了同一間就聲稱答案都正確。

R5 交接組要求從陽台聽噪音，但來源只說陽台是偏好，没有證明房源有陽台。
R6 交接組要求確認「Friday 房東訊息中的租約／押金／預付租金條件」，然而該訊息只更正交屋日期。
後者被原始裁判標記、獨立複核未標；主代理認為此來源歸屬仍值得保留為措辭／無根據細節問題，
不因第二位裁判漏抓就將其清除。詢問條件本身合理，不能暗示那些條件已在來源中出現。

原始裁判把 R5 完整、交接都判一項 critical profile 遺漏；獨立複核兩者都通過。
分歧主要在是否要重述所有 profile 欄位，包括没有改變的日期／屋齡，
不是答案採用了已撤回的舊預算或舊目的地。主表保留兩種分數。
原文複核沒有發現付款、修繕或連續無階梯通行的關鍵底線失守，
但這是 12 個合成答案的觀察，不能當成任意壓縮後都安全的保證。

R3 兩組都符合最多六個條列。R4 兩組都恰好三個編號項目，完整 164 個英文單字、交接 159 個，均在 180 個以內。
格式過關不代表檢查內容完整：R4 完整组的書桌深度遺漏就是例子。

## 5. 評分器本身也要留證據

裁判收到完整來源，卻把自己的可見範圍誤套到候選答案。
例如 A1 摘要組說「没有給我文件正文」，裁判認為這和「題目明明有三份全文」矛盾。
實際 prompt 證明摘要組没有正文；A1 補查也確實没有 D01。

來源／prompt 複查辨認出 **11 個這類 contradiction 標記及 2 個 unsupported 標記**。
它們不能當成模型撒謊的次數；缺少關鍵發現仍是任務完整性的失敗。
A2 完整組的三個 supported translation 又被放進 unsupported 欄位，顯示引用失真與事實虛構會混在一起。
另一方面，兩個 R3 真正寫錯的數字又漏過裁判。單一模型總分不足以回答「最終品質有差嗎」。

我們沒有事後修改裁判 prompt、覆蓋標籤或重跑。保存原始輸出，再分開保存兩位盲複核的來源理由，
最後增加已看過組別與成本的主代理對照註記。A2 補查對「其他未提供資料可能有同意」的限制句，
以及 R2 交接的絕對「Never sign or pay at the viewing」，也保留措辭／範圍分歧，沒有粗暴歸零。

這個發現支持下一版評估器明確取得「候選實際看過哪些資料」，並分開評：
必要事實有没有發現、所說的話有没有原文支持、引用是否精確、下一步是否有用。
下一版尚未實作或重新量測；目前結果仍以這次凍結版本為準。

## 6. 不呼叫模型的報表與控制器

[控制器實驗](controller-results-2026-09-08.md) 實作純事件 reducer，把進度、錯誤暫停、用量與報表留在程式中。
它不是部署到所有 production runner 的改版。

| 離線驗證 | 結果 |
|---|---:|
| 手寫事件 trace／事件數 | **20/20 通過，81 個事件** |
| 保存的報表快照／指定中途 oracle | 101／10 |
| 專項單元測試 | 14 通過 |
| 延後 usage 到達排列／checkpoint 恢復 | 120／101 通過 |
| 關閉 pause 防護的 mutation control | 成功抓到違反 |
| 舊版三份 compact 報表重播 | **3/3，60/60 邏輯欄位相同** |
| 該離線實驗 benchmark 模型呼叫 | **0** |

遇到第一個已接受的 provider error 就暫停後續 dispatch，已在途的完成結果仍可接收；
只有明確承認當次 pause 的 resume 才恢復。重複事件不重算，失敗嘗試的已知 token 仍計入，
缺 input／output 時總量保持 null，cache 不得大於 input。低品質答案不會觸發「重試到通過」。

20 個最終 oracle 與指定中途預期是另外手寫，没有用 reducer 自己產生預期值。
三份舊報表重播另與已保存的模型最終 JSON 比對，移除無關的 `cost_probe.facts` 包裝後 60 欄相同。
**零呼叫是執行這個確定性工作時的呼叫數；撰寫程式及 fixture 的 AI 成本不是零。**
有限、循序事件測試不證明所有併發情況、通知延遲或 provider 錯誤分類都正確。

## 7. 實務上採用什麼

1. **先消除不需要模型的回報。** 已知統計、重試資格與 pause/wait/report 判斷可用程式重現。
   這次有三份既存輸出和 20 個 trace 的證據；控制器仍需接上實際 adapter 才能用於 production。
2. **租屋交接先保存明確欄位。** 最新硬限制、已撤回條件、事實來源、估計與已證實的區別、
   備用住宿與下一步都應留下。這輪精簡省 6,435 tokens，但摘要是人工式準備，不能等同自動壓縮保證。
3. **證據分析保留可定位的原文。** 這輪每題全文只有約 8.2–8.7 千字元；
   多一次 CLI invocation 的 input 足以抵消略去正文的節省。先保留完整文件是這個小型 corpus 較合理的預設。
4. **若繼續研究補查，先修檢索選擇與停止條件。** A1 要找到 ledger，A4 要允許有根據地不補查。
   可以在更長文件、獨立新題與乾淨 affirmative control 上再測；這些是後續方向，未在本輪加跑。
5. **把錯誤型態獨立記錄。** 共同寫錯數字、精簡獨有遺漏、錯誤引用、評分器讀錯可見範圍，
   對應不同修正。不要用同一個平均分掩蓋它們。

這輪只測下一次回答，不測長對話的錯誤累積、真實找房體驗或完整工具技能。
六題租屋使用固定入口指令，但其引用的其他 skill 檔兩組都不能讀，不能稱為完整 skill 的 e2e 評估，
也没有做真實法規準確性認證。四題分析全是挑戰批准／驗證宣稱，没有乾淨的正面批准控制組；
因此不能估计錯誤拒絕批准的比率。小樣本、單次生成、合成資料及同系列模型偏差都限制外推。
