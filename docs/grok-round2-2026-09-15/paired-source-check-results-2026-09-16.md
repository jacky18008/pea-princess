## Source and artifact checks

The model in each run actually invoked `commute_compare.py`, not merely mentioned it. The official TfL resolved-stop receipts use destination stop ID `1000139`, next weekday 2026-09-17, 09:00 arrival target, door buffer zero and approximate origins: A postcode `SE3 7RS`, B a Cable Walk street midpoint mapped to nearby coordinates. A rail runs 17 minutes and arrives 08:36; B rail runs 30 minutes and arrives at the **same Rail endpoint 08:36**, each with a timetable buffer of 24 minutes before 09:00. B's 28-minute all-mode alternative ends at London Bridge **Underground** at 08:58; A/B bus alternatives have generic London Bridge Station endpoints, not confirmed rail-platform arrivals. Initial text-destination queries can return HTTP **300** ambiguity; subsequent `1000139` receipts return HTTP **200**, and that distinction remains in the raw tool/source history. Some plan timestamps are reused from earlier source/cache observations; separate model repeats do **not** independently prove new upstream availability or bedroom conditions. A's supplied advert 74.78 m² and owner-supplied address-level government EPC extract 81 m² are separate reported facts with **unverified same-unit identity**; B's exact unit, same-unit EPC, heating/bills and total monthly spend stay unknown. An outdoor noise estimate never measures a bedroom at night.

An independent host-side guard was rerun on each saved final reply and the **resolved `1000139` A/B JSONs**. It returned `review_required` for legitimate origin approximation and generic bus endpoint. The raw `paired-commute-guard-01.json` was selected correctly. An initial read-only host rerun for 02/03 accidentally selected the *generic text-destination HTTP 300* files and is retained as `paired-commute-guard-02.json`/`-03.json`; its output cannot support route acceptance. Corrected `paired-commute-guard-02-resolved.json`/`-03-resolved.json` use HTTP 200 stop-ID receipts and share the correctly selected route-review findings. This correction happened **after** the model runs, and neither the prior model replies nor archived failed guard selections were changed.

The artifact omission has a clear boundary: the deterministic recommendation validator (branch worktree) binds a recommendation to the **constraints supplied to it** and their SHA, then verifies ranking/TODO against those supplied rows. It does not compare that input's IDs/strengths to the current active requirements in the session journal. In run 02, the model built a plausible three-row subset (rent and bedrooms mandatory; 45 minutes negotiable), so the validator could check a self-consistent subset while silently leaving out before-09:00 arrival. Run 03 skipped the checker completely. The fix needs a host-owned comparison between current user-authority ledger and the actual candidate checks/outputs, with explicit typed exceptions for action-only holds, followed by a fail-closed reply/save gate. Merely adding another instruction telling the model to remember every requirement cannot enforce this property.

Independent Astra/high grading corrected its initial run-02 prose-only G3 judgment after inspecting the artifacts: **route wording passes 3/3; run 02 artifact authority fails; run 03 artifact authority is unavailable; conversational first-line/length gates fail 3/3**. Run 02's claim that *all* source plans have no wait is overbroad (some bus/all-mode routes have 1–3 minutes); run 03 restricts zero waiting to the relevant rail plan, but its last question implies quietness is an A benefit when indoor quietness remains unknown. The samples show variability in how many checks the model invokes; they do not supply a failure-rate estimate or a reliable shipping guarantee.
